# Decisions and trade-offs

Each entry records what was chosen, what else was considered, and why.

### PostgreSQL instead of SQLite
SQLite was suggested, and is simpler to ship. Postgres was chosen because the core analytics need medians and percentiles (`percentile_cont`), which SQLite lacks, and because Hibernate's SQLite support is community-maintained. Docker Compose keeps local setup to one command.

### Store salaries in local currency, convert to USD at read time
Storing USD would make comparisons trivial but would change the number HR entered and make history depend on exchange-rate updates. Local currency stays the source of truth. Insights show USD for cross-country comparison, and a local-currency median when a group is paid in a single currency.

### A static exchange-rate snapshot
Live rates would add an external dependency and make two views of the same report disagree. A versioned snapshot with its date shown in the UI keeps analytics reproducible and explainable. The cost is that rates need deliberate updates through a new migration.

### Median as the headline number
Salary data is skewed. The integration tests show one high earner pulling the average up 45% while the median stays put. Average is still shown, labelled as being pulled up by the highest earners.

### Outlier definition
An outlier is someone at least X% from the median of their peers, where peers share job title, country and currency. The comparison happens in local currency, so exchange rates cannot create false outliers. Groups under 5 people are skipped because a median of two or three people isn't meaningful. Filters change who is listed, never the peer group.

### Optimistic locking instead of last-write-wins
Two HR users editing the same record is plausible. A `version` column makes the second save fail with a clear message rather than silently losing the first person's change. Pessimistic locks would be heavier and unnecessary for this edit rate.

### JPA for CRUD, SQL for analytics
One tool for both would be more uniform, but each fits its job better. JPA gives entity mapping and locking for edits. SQL keeps aggregation in the database.

### Employee IDs are entered by HR
IDs could be generated by the system, but HR already has employee IDs from existing records and the migration from Excel has to preserve them. The API validates the format and uniqueness.

### Job title and department as free text with suggestions
Lookup tables would enforce consistency but need their own admin screens. Free text with suggestions from existing values allows new roles while nudging towards consistent spelling. Lookup tables are a natural next step.

### Salary sorting only within a country
Sorting INR and USD amounts together is misleading (₹1,500,000 looks larger than $150,000). The salary column becomes sortable once a country filter is set, and a tooltip explains why.

### Seed data: deterministic and realistic
Salaries are computed from a role base salary, a country cost factor and ±15% variation, with about 1% deliberate outliers so the outlier view has something real to find. A fixed random seed makes demos and tests reproducible. Exchange rates are reference data in a migration; employees are demo data loaded only on request, and seeding is skipped when data already exists.

### Angular Material
The assessment specifies Angular for Java roles. Material is Angular's official component library, accessible by default, and supplies the table, paginator, dialogs and form fields this app needs, which leaves effort for the product itself.

### No charting library
The only chart is the pay-range bar, a few positioned elements built from a small tested geometry function. A charting library would add bundle size for one visual.

## Deliberately not built (see REQUIREMENTS.md for full reasoning)

Authentication and roles (first priority for v2: salary data is sensitive), salary history and audit trail, bulk Excel import, payroll and tax, bonuses and equity, live exchange rates.
